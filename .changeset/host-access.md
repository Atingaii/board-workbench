`a2({ authenticate })` says who a request is. It's one function, `verifyTokens()` from `vboard/access` by default, and verifiers compose in plain code: each answers null when the request carries nothing it recognizes, and a 401 when its credential fails. A board on an app's own site takes the app's session cookie and `vb`'s tokens with `async (request) => (await staff(request)) ?? (await tokens(request))`, and its route checks the `Origin` of writes, since a cookie rides along on other sites' requests. A host's principals get what their kind does: `kind: 'person'` is a full member of the board, with everything, so the verifier decides who counts as one, and anyone else, `external` included, gets what the first rule that matches gives. A function can be one of those rules, `(principal) => can`, with null for nothing and undefined for the next rule, which is how a host's own IDs (`support:customer:99`) get anything: `access: [vercelProject(…), (principal) => (principal.id.startsWith('support:customer:') ? { 'support/': ['read', 'post'] } : undefined)]`. It's asked whenever a principal acts, a schedule's send included, and never about a person or the board's own deployments in its environment. A host serving many teams' boards passes its own verifier alone, and one function as `access`, which decides for every principal. A board whose verifier is `verifyTokens()` alone takes no host's principals. `vercelBlob({ prefix })` lets many boards share one Blob store.
