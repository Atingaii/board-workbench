Grants name principals. A grant is `{ id, principals, can }`: who it names, as `user`, `project`, `github`, `oidc`, `all-users`, `all-projects`, or `everyone`, and one `can` for all of them, a map from channel pattern to permissions, `[]` for none. `team.createGrant({ principals: [{ kind: 'everyone' }], can: { 'security/': [] } })` closes `security/`, and `team.createGrant({ principals: [{ kind: 'user', email: 'alice@acme.com' }], can: { 'security/': 'all' } })` opens it to Alice alone. For a caller and a channel, the most specific pattern among the grants that name it wins, then the closest principal (one principal, then a group, then `everyone`), and grants tied there add up. `everyone` lets no one in by itself. `access`'s rules meet the grants as principals of their kind. `team.updateGrant(id, { add, remove, can })` (`PATCH /grants/:id`) changes a grant by its ID.

Every board starts with g1, every person with everything, and g2, every project on the board's team in production, preview, and development with read, post, react, and label everywhere, as Vercel's API seeds a team's board. Changing a grant takes `manage` at each pattern it names, and listing them `manage` at `*`. A board's owners (on `vb serve`, its local user) always may.

Breaking: `{ issuer, claims, can? }` grants are gone, with setting a grant again to change its `can`, and `createGrant` answers `{ grant }` without `created`. A board on `a2()` folds the grants it kept before into nothing. A rule like `vercelProject({ project: 'prj_front', can: { 'feedback/': ['post'] } })` no longer keeps a project on the team out of the rest of the board, since g2's `*` lets it in: write `{ '*': [], 'feedback/': ['post'] }`, or revoke g2. `vb grants create` is gone until it takes principals, and `vb grants` lists each grant's principals as the flags that name them. Custom backends implement `updateGrant`, and `http()` forwards each method with its own HTTP method.
